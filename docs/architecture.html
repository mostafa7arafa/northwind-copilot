Two layers, one repo

The code splits cleanly in two. Read this section once and the rest of the document has a place to live.

Local Engine

The original proof-of-concept: a LangGraph SQL analyst over the Northwind retail database. Runs on your laptop against a local Ollama model, or inside the LangGraph dev server. No auth, no tenants, one database. Still first-class — the eval harness proves its quality and must stay comparable.

SaaS Foundation

Additive packages that turn the engine into a hosted product: users sign up, upload CSV/XLSX/SQLite, and chat with their data. Identity, per-tenant SQLite files, token metering, credit billing, BYOK keys — all built and tested, nothing deployed yet.

The dependency rule that keeps them apart

Every layer imports only the layers below it: web → response → query → infra → core. That single rule is why the SaaS work never destabilised the agent. Three consequences worth internalising:

  • The POC signatures were extended, never rewritten. build_system_prompt, build_database, build_agent_for, and run_sql each grew defaulted parameters that reproduce the exact legacy behaviour. Call them with no new arguments and you get the Northwind POC, byte-for-byte.
  • Metering has no database access. response/streaming.py can accumulate tokens into an optional meter, but it cannot write a ledger row — the DB lives one layer out, in web. Billing settles in the web layer's finally block. Dependencies point inward, so money never leaks into the engine.
  • The eval harness and the static graph are frozen. query/graph.py, core/definitions.py, SYSTEM_PROMPT, and everything under eval/ are off-limits to SaaS work, so benchmark scores stay comparable across every change.

The HOSTED_MODE flip

One boolean environment variable decides which product you are running. It is read once, at import time, into the frozen settings singleton.

ConcernHOSTED_MODE=false (POC)HOSTED_MODE=true (SaaS)
Access controlOptional shared bearer token, or fully openPer-user JWT session cookie → org context
Data sourceOne shared Northwind SQLitePer-tenant uploaded SQLite files
Conversation historyClient sends it in the requestServer owns it, rebuilt from stored turns

◆ The contract

With the flag off, the hosted routers are still mounted but never reached, and the app DB file is never created. The POC path is a supported product, not dead code. "Do not break it" is a rule, not a nicety.

A

The Local Engine Module A

The agent core. Everything here runs with no network beyond a local Ollama daemon, and boots either as a plain Python object or inside the LangGraph dev server. This is what the SaaS layer wraps — and what the eval harness grades.

Two ways it starts

The engine has one composition root, build_agent(), reached through two front doors:

  1. langgraph dev
    Reads langgraph.json, which points at ./northwind_copilot/query/graph.py:graph. Importing that module executes graph = build_agent() at module scope, so the dev server gets a fully compiled graph object to serve over its own API and Studio UI. This is the path that can later be deployed to LangGraph Platform.
  2. In-process, via the web app
    The FastAPI service ignores the static graph and instead builds a fresh agent per request through build_agent_for(config), because the web user picks their engine and dataset each turn. Same tools, same middleware, assembled dynamically.

▲ Reserved name

LangGraph reserves DATABASE_URI and overwrites it with :memory: under langgraph dev. The analyst DB is therefore read from NORTHWIND_DATABASE_URI, never DATABASE_URI. Forget this and the dev server silently queries an empty in-memory database.

What build_agent() assembles, in order

# query/graph.py — the module-level composition root def build_agent() -> CompiledStateGraph: primary = build_primary_model() # Ollama, local-first fallback = build_fallback_model() # OpenAI, or None if no key db = build_database() # Northwind SQLite, READ-ONLY sql_tools = SQLDatabaseToolkit(db=db, llm=primary).get_tools() return create_agent( model=primary, tools=sql_tools + [search_docs], # SQL + knowledge retrieval system_prompt=SYSTEM_PROMPT, checkpointer=None, # stateless; history is re-sent middleware=[EscalateToFallbackMiddleware(*fallbacks), trim_context], ) graph = build_agent() # langgraph.json target

Five decisions are baked into those eleven lines, and each is deliberate. The next subsection is the "why".

The tools, and why they were chosen

The agent is given five tools: four from LangChain's SQLDatabaseToolkit — sql_db_list_tables, sql_db_schema, sql_db_query, sql_db_query_checker — plus one custom tool, search_docs.

⊘ Read-only is the security boundary

The single most important design decision in the engine: the database connection is opened read-only at the connection level (sqlite3.connect("file:…?mode=ro")), not by inspecting whether a query string starts with SELECT. A confused — or prompt-injected — model physically cannot DROP, DELETE, or UPDATE, no matter what SQL it writes. The guarantee holds at the sqlite layer, below anything the LLM can influence.

Why the standard toolkit

Rather than hand-roll a query tool, the engine uses LangChain's toolkit so it inherits the battle-tested list-tables / describe-schema / execute loop. The read-only guarantee is imposed underneath it via the connection, so the stock tools stay safe.

Why search_docs exists

Business truth lives outside the schema: what "revenue" means, when the Summer campaign ran, the return policy. A FAISS vector search over docs/*.md injects those definitions so the model doesn't invent a margin formula. POC-only — uploaded datasets carry their own context instead.

Why the checker is dropped locally

On the web's local path, build_agent_for strips sql_db_query_checker. It is a whole extra model round-trip to lint SQL the model just wrote — negligible value on a small local model, and the step that stalls when a slow run is cancelled mid-stream. The static graph keeps it; the lean local path does not.

Why schema is injected, not discovered

In hosted mode the schema summary is introspected once and pasted into the prompt, so the model can skip the list_tables/schema round-trips entirely. A deliberate latency win; the tools remain as an escape hatch. Capped at 40 tables — retrieval is the fix at warehouse scale.

core/ — configuration & prompts (no I/O)

The innermost layer. Pure data and strings; imports nothing from the rest of the app. If it reads a file or opens a socket, it does not belong here.

settings = Settings()

core/config.py

A frozen dataclass built from environment variables (loaded from .env once, at import). Every tunable — model names, paths, token budgets, deadlines, all the SaaS knobs — resolves here so nothing downstream hard-codes a value. Helpers _env / _env_int / _env_bool strip stray surrounding quotes, because some loaders (including langgraph dev reading .env) pass values with the quotes attached.

Note  It carries two token budgets — max_context_tokens (8k, local) and max_context_tokens_cloud (32k) — and two turn deadlines, because a small local model should be cut promptly while a cloud multi-query analysis legitimately runs longer.

SYSTEM_PROMPT · build_system_prompt(...) · LEAN_LOCAL_PROMPT · GENERIC_ANALYST_PROMPT

core/prompts.py — the single home for every prompt string

SYSTEM_PROMPT is the static, 9-rule Northwind analyst prompt used by the benchmark graph. Its revenue/margin formulas are interpolated from core/definitions.py so the prose and the graded rules can never drift apart. It is byte-stable — the eval depends on it.

build_system_prompt(...) is the dynamic, request-scoped assembler used by the web service. It layers sections — data-integrity, scope, presentation, insights, ECharts — onto one of three bases depending on the request:

PathBase promptExtra sections
Local engineLEAN_LOCAL_PROMPTpresentation + insights only (latency-sensitive)
Cloud engine, NorthwindSYSTEM_PROMPT+ data-integrity, scope, ECharts
Uploaded datasetGENERIC_ANALYST_PROMPT + schema + business context + golden examples+ data-integrity, scope, presentation, insights, (ECharts if capable)

Backward-compat  When dataset_summary is None and the flags say Northwind-cloud, it reproduces the exact POC prompt. That is the defaulted-parameter contract in action. Rule 7 of the generic prompt is the "answer in the user's language" wedge (the Arabic feature); the POC prompt is untouched by it.

infra/ — database, models, retrieval

The layer that actually touches the outside world: SQLite, Ollama, OpenAI, FAISS. Everything above it is I/O-free.

build_database(database_uri=None) -> SQLDatabase

infra/database.py

Connects to a database read-only and wraps it as a LangChain SQLDatabase. For a file-backed SQLite database (the default and every uploaded dataset), it hands SQLAlchemy a custom creator that opens the file with mode=ro — writes raise OperationalError instead of touching bytes. sample_rows_in_table_info=0 keeps the re-sent schema payload small.

Extension seam  The database_uri parameter defaults to the configured Northwind DB (POC) but the hosted service passes a per-tenant dataset's SQLite URI. For a non-file backend (a future Postgres), read-only must come from the DB role's grants — the adapter connects normally and leaves that to deployment.

build_ollama_model(model) · build_primary_model() · build_fallback_model()

infra/llm.py

build_ollama_model constructs the local chat model with three measured, non-obvious options: num_ctx pinned above the trim budget (Ollama defaults to 4096 and silently truncates over-long prompts from the head, where the system prompt lives — a correctness fix, not just latency); reasoning=False (chain-of-thought cost 2.5× latency for identical benchmark accuracy); and keep_alive to keep weights resident between turns.

build_fallback_model returns an OpenAI model or None: ChatOpenAI raises at construction with no key, so a local-only user would otherwise be unable to even build the graph. The fallback is a safety net, not a requirement.

search_docs(query) · _get_index() · load_or_build_index(...)

infra/docs_tool.py · infra/rag.py

The knowledge tool. _get_index lazily builds a process-wide FAISS store on first call; load_or_build_index loads a persisted index from .faiss_index or rebuilds it (paragraph-chunking docs/*.md, embedding with OpenAI) when REINDEX is set or none exists. search_docs itself returns the top-4 chunks, tagged by source filename.

Dependency  Retrieval needs OpenAIEmbeddings, so building the index requires an OpenAI key and outbound HTTPS. On a machine that can only reach loopback, a pre-built .faiss_index loads fine but a rebuild fails.

query/ — the graph and its middleware

EngineConfig · DatasetContext · build_model(config) · build_agent_for(config, ...)

query/agent_factory.py

build_agent_for is the web's dynamic twin of build_agent. Given a frozen EngineConfig (provider / model / key) and an optional DatasetContext, it: builds the model (Ollama, OpenAI, or OpenRouter via the OpenAI SDK with a base-URL swap); builds a read-only DB for the dataset or Northwind; drops the query-checker on local; assembles the right system prompt; picks the tool set (search_docs only on the Northwind path); and chooses the trim budget by engine. It inserts EscalateToFallbackMiddleware only for a local primary with a fallback available.

Why two dataclasses  EngineConfig (inference) and DatasetContext (data source) are kept separate so a request's model and its data are independent choices — you can point any engine at any dataset.

EscalateToFallbackMiddleware · is_degenerate(response) · make_trim_context(max_tokens)

query/middleware.py

The local-first / escalate-on-empty design. A small local model sometimes returns an empty completion on the hardest reasoning step; the agent loop reads that as "done" and stops, so the failure is silent. LangChain's stock fallback middleware only retries on exceptions, so it slips through. is_degenerate catches the case — a final message with neither text nor tool calls — and the middleware escalates to the fallback chain, returning the first usable response.

make_trim_context builds a before_model hook that trims history to a token budget (keeping the most recent messages). On local it is the load-bearing guard against a tight context window; on cloud the budget is large so a curated multi-turn history survives untouched.

Async twin  It implements both wrap_model_call and awrap_model_call — the langgraph server invokes agents through astream, so without the async version the framework raises NotImplementedError.

response/ — turning the agent stream into UI events

async stream_chat(*, history, config, dataset, usage_meter, ...) -> AsyncIterator[dict]

response/streaming.py — the engine's busiest function

Runs the agent for one turn and yields the structured events that drive the frontend's pipeline rail. As tool calls and messages arrive it emits engine, stage transitions, sql, table, chart, insights, final, and finally done. The pipeline it narrates:

01understand› 02sql› 03execute› 04results› 05chart› 06insights

It re-runs every captured query through run_sql to produce clean tables, suppresses charts when no SQL returned rows (fabricated-number guard), and derives a chart server-side for local models that don't draw their own. Three exits are handled explicitly: CancelledError (client disconnected — log one line and re-raise, never swallow), TimeoutError (salvage the queries that completed, then emit a friendly error), and any other exception (log with a correlation error_id, mirror it to Sentry, hand the client only the id — raw text can leak paths and URIs).

Metering seam  The optional usage_meter is fed as updates arrive, not at the end, so a disconnect or timeout still bills for the tokens already spent. This function has no DB access — it only accumulates.

_iter_with_heartbeat(...)

Wraps the agent's async stream and injects a ping every 10s of silence. A slow local model can spend tens of seconds before its first token, during which no SSE bytes flow and proxies drop the connection. The in-flight __anext__ is held in a task and only observed with a timeout, so a heartbeat never cancels the real work.

_parse_final(content)

Splits the model's final message into prose, insight bullets, and any fenced echarts blocks (a capable model may draw several). Strips Markdown tables the model drew — the UI already renders the real result set, so they'd show as raw pipes.

_Rail

A tiny state machine that tracks which pipeline stages are done/active and emits only the transition events, so the frontend rail advances monotonically without the caller managing stage bookkeeping.

LangSmith tracing

Built explicitly (an lru-cached client) rather than via env auto-tracing, so INSECURE_TLS can relax cert checks on trace uploads. A session_id in run metadata groups every turn of a conversation into one thread.

run_sql(sql, db_path=None) · infer_chart(table)

response/charting.py

run_sql re-executes the agent's final SELECT directly against the SQLite file so the frontend gets structured columns/rows instead of the string blob the SQL tool returns. It opens read-only, refuses anything that isn't SELECT/WITH, installs a SQLite progress handler that aborts a query past the time budget (so a runaway cartesian join can't pin a core), and caps at 500 rows with a truncated flag. Any error returns None rather than raising.

infer_chart derives a reasonable ECharts option from a result table: first non-numeric column as the category axis, numeric columns as series, a line for temporal categories and bars otherwise. This is how local (and chart-less cloud) turns still get a chart.

Problems & sharp edges in the engine

RAG rebuild needs the cloud
Building the FAISS index requires OpenAI embeddings and outbound HTTPS. In a loopback-only sandbox a pre-built index loads, but REINDEX=true fails. The index is also loaded with allow_dangerous_deserialization=True — fine for a self-built file, a footgun if the .faiss_index ever came from an untrusted source.
Silent head-truncation if num_ctx is misconfigured
If OLLAMA_NUM_CTX drops below the trim budget, Ollama truncates the prompt from the head and drops the system prompt (and, hosted, the schema summary) with no error. The trim middleware is only a real guard when the window it trims to actually exists.
The static graph and the web path can diverge
graph.py:graph is local-first with the checker kept; the web builds a different agent (checker dropped, per-engine prompt). They share helpers but are assembled separately, so a change to one is not automatically reflected in the other. The eval only exercises the static graph.
Server-side chart inference is heuristic
infer_chart guesses axes from column names/types. A table whose only category column is an id, or whose numbers are codes, can produce a misleading chart. It bails on <2 rows and pure-id series, but it cannot know semantics.
B

The SaaS Foundation Module B

Additive packages that make the engine a hosted, multi-tenant product. They sit on the outer edge of the dependency graph: they call the engine, the engine never imports them. Every one of these was built and tested; none is deployed.

How the server starts

The hosted product is served by uvicorn, not the langgraph dev server. The container's command tells the whole story:

# deploy/Dockerfile.backend CMD ["sh","-c","alembic upgrade head && uvicorn northwind_copilot.web.app:app --host 0.0.0.0 --port 8000"]
  1. alembic upgrade head
    Applies migrations 001→007 against Postgres, bringing the app (control-plane) schema up to date: identity + tenancy, datasets, conversations + turns, usage + credit ledger, api_keys, subscriptions + webhook_events, and turn feedback + golden examples.
  2. import web.app
    init_sentry() runs (a no-op unless SENTRY_DSN is set). CORS is configured from settings. All five hosted routers — auth, datasets, conversations, keys, billing — are mounted unconditionally; they simply aren't reachable with the flag off.
  3. lifespan startup
    In hosted mode over a SQLite app DB (dev/test only), create_all() builds the schema so no migration step is needed. Over Postgres (production) this is intentionally skipped — Alembic owns the schema there, and create_all would drift from the migration history.
  4. serve
    Requests hit require_access, which resolves the session cookie to a RequestContext in hosted mode, or falls back to the shared-token guard (returning None) in the POC.

web/ — the FastAPI app & its guards

app = FastAPI(...) · lifespan · POST /api/chat · GET /api/usage · /api/models · /api/preferences

web/app.py

The orchestrator. /api/chat is the heart of the product and gets its own lifecycle walkthrough below. In short, per turn it: resolves the API key (distinguishing BYOK from metered), runs the pre-flight credit check, builds the EngineConfig, resolves the org-scoped dataset, rebuilds server-owned history, streams via stream_chat, and — critically — settles usage and persists the turn in a finally block so a disconnect or timeout still bills and saves.

/api/usage assembles the caller's plan, remaining credits, trial counters, BYOK providers, and subscription status to drive the usage meter. In the POC (no tenant) it returns {"hosted": false} so the frontend just hides the meter.

Deferred imports  Every tenancy/metering import inside these handlers is done lazily, so the POC path never touches the application database nor creates its file.

require_access(...) · require_auth(...) · rate_limit(request) · RateLimiter

web/security.py

The mode-aware door. require_access branches on hosted_mode: hosted, it reads the httpOnly nw_session cookie, verifies the JWT, loads the user + org, and returns a RequestContext; POC, it enforces the optional shared bearer token (constant-time compared to defeat timing attacks) and returns None. rate_limit is a per-process in-memory sliding window.

Deliberately minimal  Auth and rate limiting are dependency-free so a self-hoster can stand the service up on one box. Both are single-node assumptions — a multi-worker deployment needs a shared store (Redis) for the limiter.

_resolve_hosted_key(...)

Decides BYOK vs metered: the org's stored (encrypted) key wins, then a request-body key — both are the customer's own account, so those turns are BYOK (recorded, never charged). Only when neither exists does the turn run on the server's key and get metered.

_resolve_api_key(...)

Guards the operator's wallet: the server's env key is used only for trusted callers (hosted users or a token-gated deploy). An anonymous open POC never spends the operator's key for a visitor who didn't bring one.

models_registry.list_all_providers()

Reads installed Ollama models live from the daemon (hidden in hosted mode — no local daemon there) and offers a curated cloud list. Hosted defaults to OpenRouter (the metered key); the POC leaves OpenAI first.

web/preferences.py

Persists free-text analyst preferences to a single JSON file with an atomic temp-file-then-rename write. Simple and safe — but see the problems list: it is process-global, not per-tenant.

tenancy/ & auth/ — who is asking, and for which org

get_engine() · get_sessionmaker() · get_session() · create_all()

tenancy/db.py

A single process-wide async engine, created lazily from APP_DATABASE_URL — SQLite+aiosqlite in dev/tests, Postgres+asyncpg in production, chosen entirely by the URL so no code changes between them. get_session is the FastAPI dependency that yields a request-scoped session and manages the commit/rollback boundary so handlers don't each have to.

Base · User · Org · OrgMember · Dataset · Conversation · Turn · UsageEvent · CreditLedger · Subscription · WebhookEvent · ApiKey · TurnFeedback · GoldenExample

tenancy/models.py — the control-plane schema

Everything about the product, separate from the per-tenant SQLite files that hold each customer's data. Two design choices thread through it: the org is the tenant unit from day one — signup creates a personal org, so adding team seats later is a row change, not a migration — and string UUIDs + timezone-aware timestamps throughout, so the same models run on Postgres and SQLite unchanged. Turn's JSON columns mirror the exact SSE artifact the frontend renders, which is what lets the server own conversation history.

RequestContext · current_user(...) · load_context(session, user_id) · current_org(...)

tenancy/deps.py

load_context resolves a user to a frozen RequestContext(user_id, org_id, plan, role) — the object every downstream route authorises against. v1 assumes one personal org per user (the first membership); multi-org selection later reads an active-org claim here.

hash_password · verify_password · mint_session_token · read_session_token · signup/login/logout/me

auth/service.py · auth/router.py

Passwords are argon2id (memory-hard, current OWASP default). Sessions are stateless JWTs delivered as an httpOnly cookie, so the token is never readable by JavaScript — no localStorage XSS exposure. The cookie is Secure in hosted mode (always HTTPS behind Caddy), relaxed on http://localhost in dev.

signup atomically provisions a User + personal Org + owner OrgMember + 14-day trial in one transaction, so every user has a tenant from the very first request. Response bodies never contain the token.

⊘ Tenant isolation is the highest-stakes invariant

Every data route re-checks dataset.org_id == ctx.org_id and answers a uniform 404 when it fails — the same response whether the row is missing or owned by another tenant, so the API never even confirms another org's data exists. On disk, each org's files live under {tenant_data_dir}/{org_id}/, making isolation a filesystem fact as well as an application check. "Org A cannot read org B" is the test class that must never regress.

datasets/ — untrusted files become read-only SQLite

ingest(source_type, data, dest) · ingest_csv / ingest_xlsx / ingest_sqlite · append(...) · dataset_stats(...)

datasets/ingest.py

Uploaded bytes are untrusted, and the ingestion posture reflects that. CSV/XLSX are parsed with pandas and written to a fresh SQLite file, so nothing executable survives. An uploaded SQLite file is the dangerous case — it can carry triggers, views, or virtual tables — so it is never served directly: it's opened read-only, integrity-checked (PRAGMA quick_check), and only real table data is copied into a fresh file, shedding all executable objects. Column and table names are coerced to safe identifiers.

append is what makes datasets relational across files: each added upload becomes more tables in the same per-tenant DB (de-conflicted with an _N suffix, never clobbered), so the agent can join sales.csv against targets.xlsx. dataset_stats re-counts from the file afterwards, so a partial multi-sheet append still leaves accurate stored counts.

schema_summary.py

mechanical_summary introspects tables, columns, types, row counts, and 3 sample values per column into the block that gets injected into the prompt. An optional describe callable can LLM-enrich it into prose — the hook exists but is currently unused (a future item).

storage.py

Owns the {tenant_data_dir}/{org_id}/{dataset_id}.sqlite layout, per-org disk usage (a single glob-walk), and file deletion. Keeping each org in its own directory is what makes isolation a filesystem fact.

golden.py — select_examples(...)

Picks up to 3 confirmed (question→SQL) pairs to inject for a dataset, ranked by plain keyword overlap with the incoming question, recency as tie-break. Deliberately no embeddings in v1 — the per-dataset corpus is tens of examples, and the goal is formula/style transfer, not retrieval precision.

router.py

Upload, add-file, run-query, list, get, edit-context, delete — every route _load_owned-guarded to the caller's org. The user-edited SQL route runs through the same read-only + timeout + row-cap path as the agent (run_sql), so an edited query can do nothing the agent couldn't.

conversations/ — the server owns history now

TurnRecorder · ensure_conversation(...) · persist_turn(...) · build_history(turns, question)

conversations/service.py · conversations/history.py

In the POC the client sends the whole conversation in each request. Once tokens cost money, that is a hole — a client could forge an assistant "memory" to smuggle content into the prompt. So in hosted mode the server owns history: only the new question comes from the request; all prior context is rebuilt from stored turns by build_history (last 5 turns, each replayed as the question plus a compact recap of the answer and its executed SQL + a few result rows).

TurnRecorder observes the very same SSE events the client renders and accumulates them into a storable Turn; persist_turn writes it. Because the chat endpoint drives the recorder and calls persist_turn in a finally, a turn is saved even if the client disconnects mid-answer.

metering/ & billing/ — counting tokens, charging credits

Three settlement modes are decided per turn. Understanding them is understanding the whole money model:

ModeWhenWhat is written
MeteredPaid plan, running on our provider keyUsageEvent + a credit_ledger debit; cached balance decremented under a row lock
BYOKOrg's own stored keyUsageEvent with byok=True, credits=0; no ledger write — recorded for fair-use analytics only
TrialNo credit grant yetUsageEvent with the real credit cost (for visibility); no ledger write — the trial is capped by days + query count, not balance

UsageAccumulator.observe(message) · price_for(model) · credits_for(model, in, out)

metering/usage.py · metering/pricing.py

UsageAccumulator is the object handed to stream_chat. It folds each AIMessage.usage_metadata into running input/output totals, de-duplicating by message id because a graph update can replay already-seen state. LangChain normalises token counts across OpenAI-compatible backends and Ollama alike, so one accumulator covers every engine.

pricing.py holds a static per-model rate card and converts tokens → USD → credits (1 credit ≈ $0.01). All money math is Decimal, quantised to 4dp to match the Numeric(12,4) columns — never float. An unknown (free-typed) model falls back to a deliberately high frontier price, so it can never be under-billed.

check_and_reserve(...) · settle(...) · grant_credits(...) · trial_queries_used(...)

metering/credits.py

check_and_reserve is the pre-flight, run before any model call: BYOK bypasses every check; trial is gated on expiry + query count; paid requires a positive balance. It raises 402 Payment Required when the allowance is exhausted, so an out-of-credit turn is rejected before it spends anything.

settle is the post-flight, called from the chat endpoint's finally. It always writes a UsageEvent, and for metered turns adds a ledger debit and updates orgs.credit_balance under SELECT … FOR UPDATE — a real row lock on Postgres serialising concurrent turns, a no-op on the SQLite dev backend. The ledger is the auditable source of truth; the balance column is just a cache so entitlement checks are a single-row read.

Entitlements · PLANS (trial/starter/pro/team) · get_entitlements(plan) · require_entitlement(feature) · ensure_upload_allowed(...)

billing/entitlements.py — the tier sheet as code

Plans are frozen dataclasses in code, not an enum migration, so a tier change is a code edit. Each defines credits/month, dataset count, upload cap, BYOK availability, seats, and trial caps. require_entitlement("byok") builds a FastAPI dependency that 403s when a plan lacks a feature; ensure_upload_allowed enforces dataset-count (403) and file-size (413) quotas.

BillingProvider (Protocol) · NormalizedEvent · get_provider() · MockBillingProvider · apply_event(session, event)

billing/provider.py · billing/mock.py · billing/service.py

Everything the app knows about payments goes through the BillingProvider protocol: build a checkout URL, build a portal URL, and turn a webhook into a NormalizedEvent. The lifecycle code only ever sees normalized events, so adding a real processor (Paddle) is one new module + one branch in get_provider() — no changes to routes, service, or frontend.

MockBillingProvider walks the exact real path with no money: checkout returns a URL, opening it "completes payment", and completion is delivered as a JWT-signed webhook through the same parse → verify → idempotent-apply pipeline. The signature stands in for a provider's webhook signature; the token's jti stands in for its event id (replays are idempotent); the expiry bounds link validity.

apply_event is the provider-agnostic lifecycle: activated sets the plan + grants monthly credits + upserts an active subscription; renewed expires the old balance (credits don't roll over) and grants a fresh month; payment_failed marks past_due (grace period); cancelled demotes to an expired trial — data stays readable, chat answers 402. Every application records the provider event id in webhook_events first, so retried deliveries are no-ops.

keys/ & observability

store_key(...) · resolve_org_key(...) · delete_key(...) · list_keys(...)

keys/service.py

BYOK provider keys are Fernet-encrypted with KEY_ENCRYPTION_SECRET before they touch the database, and the plaintext is only ever reconstructed server-side at the moment a chat turn needs it (resolve_org_key). The API is write-only by contract — it returns only {provider, last4, set_at}, never the key. A row that fails to decrypt (e.g. after a key rotation) resolves to None and the turn quietly falls through to the metered path rather than erroring.

init_sentry() · report_error(exc, error_id) · _scrub_value(...)

core/observability.py

Opt-in error tracking (only when SENTRY_DSN is set) and safe to run without the SDK installed. Every outgoing event passes through a scrubber that redacts provider-key and bearer-token shapes, so a stray key in an exception message can never reach a third party. The error_id a user sees in a failed chat becomes the Sentry tag to search by.

Problems & sharp edges in the SaaS layer

Analyst preferences are process-global, not per-tenant
web/preferences.py stores one JSON file for the whole process and /api/chat loads it for every request regardless of tenant. In hosted mode that means one org's saved preferences would apply to all orgs. Fine for the single-user POC; a real leak in multi-tenant mode. Preferences need to move onto the org (or user) row.
Rate limiting is per-IP and per-process
The limiter keys on client IP in an in-memory window. Behind a shared NAT many users collide; across multiple workers the limit multiplies. Hosted mode wants a per-user_id key in a shared store (Redis) — noted as open product work.
Ingestion is synchronous, bounded at 25MB
Uploads are parsed in-request with a hard 25MB ceiling, independent of the Pro/Team 200–500MB plan caps, because a large file read into memory would stall the single worker. Background ingestion is the unlock for the bigger tiers.
The credit row-lock is a no-op in dev
SELECT … FOR UPDATE only truly serialises on Postgres. On the SQLite dev/test backend it does nothing, so concurrency behaviour can't be validated locally — it must be checked against the Docker/Postgres stack.
Graders only prove Northwind competence
The eval harness exercises the static Northwind graph, not the dynamic uploaded-dataset path. Until a second eval dataset runs through build_system_prompt's dataset branch, "it works on someone else's data" is asserted, not measured. This is called out as the #1 product risk.
C

One hosted turn, end to end

The two layers meeting in POST /api/chat. Follow a single question from cookie to settled credit — this is where every earlier decision pays off.

  1. Guard & identify SaaS
    require_access reads the nw_session cookie, verifies the JWT, loads the user + org, and returns a RequestContext. rate_limit checks the window. (POC: token check, ctx = None.)
  2. Resolve the key & pre-flight the wallet SaaS
    _resolve_hosted_key decides BYOK vs metered; check_and_reserve raises 402 if the trial/credit allowance is spent. No model has been called yet — an out-of-allowance turn costs nothing.
  3. Scope the dataset & rebuild history SaaS
    _resolve_dataset loads the org-owned SQLite (404 if not theirs, 409 if still ingesting) plus its golden examples; _prepare_conversation creates/finds the conversation and rebuilds server-owned history from stored turns. Only the new question comes from the client.
  4. Assemble the agent Engine
    build_agent_for(config, dataset=…) picks the model, opens the dataset read-only, drops the checker on local, assembles the dataset-aware prompt, and wires the trim (+ escalation) middleware.
  5. Stream the pipeline Engine
    stream_chat runs the agent, narrating understand → sql → execute → results → chart → insights as SSE events, re-running each query through read-only run_sql, feeding the UsageAccumulator as tokens arrive, and heart-beating through silences.
  6. Record as it flows SaaS
    A TurnRecorder observes the same events the browser does, accumulating the storable turn in parallel with rendering.
  7. Settle & persist — exactly once SaaS
    On done (and again in finally, guarded by a finalized flag) _finalize_turn writes the turn, settles usage (ledger debit for metered turns), and injects turn + usage SSE events before done. Because it's in finally, a disconnect or timeout still bills and saves.

◆ Why the layering holds

Steps 4–5 are pure Engine and know nothing about orgs or credits. Steps 1–3 and 6–7 are pure SaaS and never reach into the agent's internals — they pass a config in and read an event stream out. The seam between the two layers is exactly the stream_chat signature, and that is the whole point.

What's next

The owner's July 2026 decision: use and test the app as a product now; defer everything that needs a third party. Two tracks.

Product work — no third party needed

Second eval dataset #1 risk

Run a non-Northwind dataset through the dynamic-prompt path and grade it. Until then, quality on customer data is unproven. Then design-partner evals.

LLM schema enrichment

The describe hook in schema_summary.py exists but is unused. One cheap call per upload would turn the mechanical table dump into a readable overview.

Per-user rate limiting

Key the limiter on user_id in hosted mode and move it to a shared store, replacing the per-IP per-process window.

Background ingestion > 25MB

A task queue unlocks the Pro/Team upload caps currently bounded at 25MB by synchronous in-request parsing.

Fix per-tenant preferences

Move analyst preferences off the process-global JSON file onto the org/user row before hosted launch (see problems).

Self-host Monaco

The SQL editor loads Monaco from jsDelivr at runtime; self-hosting removes the CDN dependency and the CSP carve-out.

▲ Sandbox reality

The Claude Code Bash sandbox blocks outbound HTTPS, so cloud LLMs, OpenAI embeddings, and LangSmith all fail there — only loopback (Ollama) works. Validate cloud paths against the Docker stack, not the sandbox.
